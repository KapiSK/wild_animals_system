# 3層構成の信頼性改善（項目1〜8）

対象は `KD_edge_cam/esp/camera` → `KD_pi_server` → `original_server`。
保存・再送・重複排除の共通仕様です。HTTPに加えて、カメラ→PiのSFTP/FTP、Pi→クラウドのSFTPにも対応しました。
現在の推奨構成は [両区間SFTP](camera_sftp_delivery.md) です。
通信方式の設定と導入手順は [FTP/SFTP構成](ftp_sftp_delivery.md) を参照してください。

## 変更内容

| 項目 | 実装 |
|---|---|
| 1. 正しい受領確認 | ファイルの一時保存・fsync・検証・確定・SQLite登録後に200を返す。容量不足は507、不正データは422、同じ画像IDで内容が異なる場合は409、それ以外の保存失敗は500。送信側はJSONのstatus、receipt_id、sha256も照合する。 |
| 2. 永続キュー | SQLiteに受信画像・推論結果・推論/転送/通知ジョブを記録。失敗は指数バックオフで再試行し、再起動後も継続する。 |
| 3. 重複排除 | 元のデバイス/サイクルIDと画像番号の組を一意に管理。クラウドの連番も元イベントとの対応を永続化し、5分経過や別イベントの到着で変更しない。 |
| 4. 通信断・欠け | カメラは全世代の未送信サイクルを巡回する。1〜2枚でも存在する画像を送信。サーバーは300秒経過した不完全サイクルも処理し、後着画像で結果を更新する。 |
| 5. 処理分離 | Piは推論とクラウド転送、クラウドは推論・集計・SMTP通知を別ワーカーで処理。モデル処理とSMTPはイベントループから外す。 |
| 6. 整合性・容量 | SHA-256、サイズ、画像デコードを確認。Piの削除対象は完了済みサイクルのみ。カメラのSD整理処理を呼び出し、未送信アーカイブは削除しない。ログはローテーションする。 |
| 7. 評価 | Piのしきい値を設定化。陰性サイクルを既定で1%抽出してクラウドへ送り、見逃し確認に利用する。推論省略はnegativeと区別してskippedと記録する。 |
| 8. 計測 | UTC受信時刻、推論時間、転送時間、実際の転送状態、再試行回数を永続記録。重なり得る処理時間を引き算して「待ち時間」を作る処理を廃止する。 |

## 配置と更新順序

共通モジュール `pipeline_common.py` と `file_transfer.py` を両サーバーの親ディレクトリへ一緒に配置します。
FTP/SFTP受信を使う場合は `transfer_receiver.py` も配置します。
従来どおり、それぞれのサーバーディレクトリから起動できます。

```text
deployment/
├── pipeline_common.py
├── file_transfer.py
├── transfer_receiver.py
├── KD_pi_server/
│   ├── main.py
│   └── detector.py
└── original_server/
    └── server.py
```

1. クラウドと共通モジュールを更新し、サーバーを再起動。
2. Piと共通モジュールを更新し、サーバーを再起動。
3. カメラのスケッチを書き込み。

カメラ/Piの新しい送信側は、新しい受領確認JSONを要求します。
古い受信側へ送った場合は完了扱いせず再試行するため、受信側から更新してください。
クラウドは従来のmultipart送信も受け付けますが、旧クライアントがハッシュを送らない場合は
送信元とのハッシュ照合まではできません。Piからの新しい送信はハッシュとサイズを必ず送ります。

Python 3.10以上を使用します。まず各サービスをUvicornの1 workerで運用してください。
SQLiteファイルは各ホストのローカルディスクに置き、NFSなどでホスト間共有しないでください。
既存のモデルとrequirementsを使い、追加のRedis/RabbitMQサービスは不要です。

今回の作業では実機への書き込み、稼働サーバーへのデプロイ、実メール送信は実施していません。

## 設定

### Pi

| 環境変数 | 既定値 | 意味 |
|---|---|---|
| `PIPELINE_DB` | `UPLOAD_DIR/pipeline.sqlite3` | 受領確認・キュー・結果DB |
| `CYCLE_TIMEOUT_SECONDS` | `300` | 最初の受信から不完全サイクルを処理するまでの秒数 |
| `MIN_FREE_MB` | `64` | 新規受信時に残すディスク容量 |
| `RETENTION_DAYS` | `7` | 処理完了画像の保存日数。未転送サイクルは対象外 |
| `EDGE_MODEL_PATH` | `best.onnx` | エッジ推論モデル |
| `EDGE_CONFIDENCE` | `0.004` | 既存の推論しきい値を維持。評価してから調整する |
| `NEGATIVE_SAMPLE_RATE` | `0.01` | 陰性サイクルの評価用転送率。0で無効、1で全件 |

HTTP転送では既存の`MAIN_SERVER_URL`を使用します。SFTPでは専用の接続設定を使用します。
`LOCAL_MODE=True`のときはどちらも転送せず、転送対象画像を未送信のまま保護します。
Piの新規画像は`UPLOAD_DIR/images/`、ログは`UPLOAD_DIR/logs/`へ保存します。
旧バージョンの`UPLOAD_DIR`直下の画像は変更・削除せず残します。

### クラウド

| 環境変数 | 既定値 | 意味 |
|---|---|---|
| `PIPELINE_DB` | `original_server/pipeline.sqlite3` | 受領確認・推論・通知キューDB |
| `CYCLE_TIMEOUT_SECONDS` | `300` | 不完全サイクルの待機時間 |
| `MIN_FREE_MB` | `64` | 新規画像受信時に残すディスク容量 |

通知は1つの元サイクルにつき1ジョブです。後着画像はイベントメタデータを更新しますが、
既に通知したサイクルへ再通知はしません。初回通知が不完全サイクルだった場合、通知内容は
その時点の画像に基づきます。クラウドの既存画像保存期間は変更していません。

## 時刻とメトリクス

カメラは撮影前にネットワーク接続しないため、撮影時点ではUTCが分からない場合があります。
現在の起動中にPiの`/healthz`からUTCを取得できた場合のみ、稼働時間の差から撮影時刻を推定し、
`captured_at.txt`に記録します。通信遅延を含む概算値で、厳密な時刻同期ではありません。
オフラインの過去サイクルには現在の日時を割り当てず、不明として扱います。
SDには`capture_meta.json`で起動後の撮影開始時刻と所要時間も残します。
PiとクラウドはOSの時刻同期を有効にして使用してください。

カメラのログは`/logs/esp.log`、`/logs/serial.log`と各サイクルの`esp_chunk.log`へ保存します。
共有ログは`.1`へのローテーションで上限を設けます。以前の日付別ログは自動削除しません。

画像単位のメトリクスをCSV出力できます。

```bash
python pipeline_common.py --db KD_pi_server/uploads/pipeline.sqlite3 --output edge_metrics_v2.csv
python pipeline_common.py --db original_server/pipeline.sqlite3 --output cloud_image_metrics.csv
```

- `edge_decision`: positive / negative / skipped。skippedを陰性と数えないでください。
- `forwarded`: 転送ジョブがdoneのときだけtrue。動物を検出しただけではtrueになりません。
- `save_ms`: 受信開始からファイル受信・検証完了まで。DB登録の所要時間は含みません。
- `forward_ms`: 最後に成功したクラウド転送試行の所要時間。
- `end_to_end_ms`: Piの受信からクラウド受領確認まで。再試行待ちを含むUTC時刻差です。
- `cloud_target_count`: クラウドでの検出数。陰性サンプルの結果確認に使用できます。

クラウドの画像メトリクスには転送ジョブがないため、`forward_state`は空です。
クラウド集計ログは`cloud_metrics_v2.csv`へ記録します。メール送信時間は通知ワーカーの
`[PERF]`ログに記録し、集計時間に混ぜません。

キューの状態はSQLiteで確認できます。

```sql
SELECT kind, state, count(*) FROM jobs GROUP BY kind, state;
SELECT key, attempts, error FROM jobs WHERE state != 'done';
SELECT cycle, idx, result FROM images ORDER BY received DESC LIMIT 30;
```

Piの`/healthz`にも空き容量とキュー件数を含めています。
陰性サンプルだけから全体精度を断定せず、サイクル単位・昼夜別で正解ラベルと比較してください。

## 再試行・保持の仕様

- カメラは全アーカイブを巡回し、1回の起動で最大3サイクルを試行。
  前回の試行位置を保存し、失敗する古い画像だけに偏らないようにします。
- 送信処理は60秒を目安に新しいリクエストの開始を打ち切り、各HTTP操作にもタイムアウトを設定。
  進行中の操作やSD処理の時間があるため、起動全体の厳密な60秒上限ではありません。
- サーバーの再試行間隔は最大1時間まで増加。試行回数で画像を破棄しません。
- 実行中にサーバーが停止したジョブは、最長約120秒のリース期限後に再取得します。
- 不完全サイクルへの後着画像も同じIDに追加し、既存の推論結果を再利用します。
- 削除後も受領確認レコードは残し、送信側の応答喪失による再送を重複処理しません。
- DBと画像をセットでバックアップしてください。DBだけ削除すると重複排除情報が失われます。
- 更新前の画像は自動的に新しいDBへ取り込みません。旧データの再処理は重複通知を避けるため
  個別に扱ってください。新しい形式で受け付けたデータから永続キューが有効です。

SMTPは「サーバーが受理した直後に接続が切れた」場合に成否を完全には区別できません。
安定したMessage-IDを付けますが、そのケースの再送による重複メールは完全には排除できません。
また、保持期限を過ぎて削除済みの陰性画像を、非常に遅い後着陽性によって復元することはできません。

## 検証

リポジトリのルートから実行します。テストは一時ディレクトリを使用し、モデル推論・SMTPはモックです。

```bash
python -m unittest discover -s tests -p test_delivery_pipeline.py -v
arduino-cli compile --fqbn esp32:esp32:XIAO_ESP32S3:PSRAM=opi KD_edge_cam/esp/camera
```

実機ではWi-Fi切断、Pi/クラウド再起動、SD容量不足、受領確認直前の切断を確認してください。
