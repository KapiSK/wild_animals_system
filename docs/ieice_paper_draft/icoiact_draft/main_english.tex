\begin{abstract}
Wildlife damage to agricultural crops is a serious issue in rural and mountainous areas of Japan, where continuous monitoring is required under limited communication infrastructure and cost constraints. This paper presents a low-cost and communication-efficient edge--cloud monitoring system using multiple trail cameras for wildlife damage control. The proposed system consists of three layers: edge cameras, an edge server, and a cloud server. Multiple cameras are connected to the edge server through a local area network, allowing multiple cameras to share a single cellular connection. To reduce the number of images forwarded to the cloud, the system employs a two-stage animal detection process. A lightweight AI model, YOLOv8n, is deployed on the edge server to filter out empty shots caused by environmental factors such as wind and vegetation movement, while MegaDetector v5a performs cloud verification before alerts are issued. Edge filtering reduced the number of capture events selected for transmission by 81.2\% during daytime and 50.7\% at night. Recall relative to MegaDetector reference labels was 93.8\% and 68.4\%, respectively, indicating a need to improve nighttime detection.
\end{abstract}

\section{Introduction}
Wildlife damage is a severe problem in Japan, with crop damage reaching 18.8 billion yen in FY2024; thus, wildlife control is an urgent issue \cite{maff}.

Effective countermeasures require information on when and where animals are present, together with timely alerts. Conventionally, wildlife monitoring for this purpose has relied on automatic trail cameras equipped with passive infrared (PIR) sensors \cite{Tabak2019,Beery2019,rs18030502}. These devices record images on SD cards for later manual collection. IoT-based monitoring systems with remote notifications and satellite-connected camera traps have been developed to provide timely information \cite{Whytock2023,Patkar2025,9345858}.

However, large-scale deployment of communication-based cameras faces cost and efficiency challenges. First, false triggers can produce "empty shots" containing no animals \cite{Beery2019}. This increases communication traffic and requires manual image sorting. Second, individual LTE contracts and expensive camera units inflate initial and operational costs. Furthermore, existing edge AI cameras consume significant power, requiring bulky solar panels or high-capacity batteries for off-grid operation \cite{Sato2022}. These factors restrict installation locations and act as major barriers for farmers and local governments.

To address these challenges, approaches such as deep learning for accurate animal detection \cite{10394750,10126065}, empty shot elimination \cite{Tabak2019,Beery2019,VELASCOMONTERO2024102815}, and edge-device power saving \cite{IEICE2020,Sato2022,VELASCOMONTERO2024102815} have been explored. Building on these approaches, we investigate how to distribute image acquisition, filtering, and notification across a shared monitoring network.

We propose a three-layer system comprising capture-only edge cameras, a shared edge server for YOLOv8n filtering, and a cloud server for MegaDetector verification and notification. A local WLAN connects the cameras to a shared LTE uplink, avoiding individual cellular contracts. Intended targets include wild boars, sika deer, Japanese macaques, Japanese serows, bears, raccoon dogs, and foxes. The system detects animal presence rather than identifying these species individually. We evaluate transmission reduction, agreement with reference detections, power consumption, communication range, and notification processing time.

\section{Related Work}

Deep learning has been widely used to streamline wildlife monitoring. Tabak et al. \cite{Tabak2019} trained convolutional neural network (CNN) models using a large-scale camera trap image dataset, reporting approximately 98\% species-classification accuracy on their U.S. evaluation images. MegaDetector \cite{Beery2019} is a general-purpose object detection model pre-trained on camera-trap images from diverse geographic regions. Fennell et al. \cite{Fennell2022} reported that MegaDetector can detect animals accurately while limiting missed detections. Hitchcock et al. proposed a semi-automated workflow combining a general-purpose detector, a species classifier, and manual verification \cite{rs18030502}. Mulero-P{\'a}zm{\'a}ny et al. combined a global model with group-specific expert models, including re-evaluation of images initially classified as background \cite{Mulero2025}.

Satellite-based alerts extend monitoring beyond terrestrial coverage \cite{Whytock2023}. Raspberry Pi systems support edge detection with YOLOv8n \cite{Patkar2025} and tracking-based suppression of duplicate transmissions \cite{Computers2025}. Other applications include YOLO-based intrusion detection \cite{10716895,11459678}, PTZ tracking \cite{SMC2024}, and PIR-triggered alerts \cite{11337723}. However, the power requirements of inference-capable camera nodes remain a concern for off-grid deployments \cite{IEICE2020,Sato2022}.

Sato et al. separated public-network communication into a parent node to reduce the power requirements of child nodes, which retained animal detection and alerting functions \cite{Sato2022}. To reduce system costs and communication delays, a hierarchical edge computing approach that delegates main processing to gateway devices like Raspberry Pi has been proposed \cite{8912138}. Furthermore, an IoT architecture linking edge inference with a cloud database has also been constructed \cite{9345858}. When inference is performed at each camera, computational and power requirements must be addressed at every deployed node. Saito et al. used a low-power auxiliary board to switch off the Raspberry Pi during idle periods \cite{IEICE2020}. More recently, SPARROW has connected peripheral cameras and sensors to a local hub for edge processing before cellular or satellite transmission \cite{SPARROW2026}. This provides a relevant precedent for aggregating sensing data and computation before wide-area communication. Harits et al. implemented an aquaculture system linking ESP32 sensor nodes to a Raspberry Pi 4 gateway for intrusion prevention and encryption before cloud storage \cite{Harits2025ECIS}, illustrating an intermediate processing layer between sensors and cloud services. The present study applies local aggregation to wildlife damage monitoring, with capture-only cameras, lightweight filtering on a shared edge server, and cloud-side animal verification.

Monitoring can also support active countermeasures, including remotely activated monkey traps \cite{8716170} and species-dependent ultrasonic deterrents \cite{11324419}. Integration with such systems is a possible future application of the monitoring network.

\section{Proposed System}
The proposed system separates image acquisition, edge filtering, and cloud verification. Cameras transfer images without performing inference, with battery-powered operation as a design goal. Following the communication aggregation concept in \cite{Sato2022} and the local-hub approach also used by SPARROW \cite{SPARROW2026}, a shared edge server filters capture events before wide-area transmission; the cloud provides a second check before notification.

\subsection{System Architecture}
The overall configuration of the proposed system is shown in Fig.~\ref{fig:system}. This system consists of the following three main nodes and the network connecting them:
\begin{enumerate}
    \item \textbf{Edge Camera}: Image acquisition and transfer to the edge server.
    \item \textbf{Edge Server}: Image aggregation, edge filtering with YOLOv8n, and transfer to the cloud server.
    \item \textbf{Cloud Server}: Cloud verification with MegaDetector v5a, data storage, and user notification.
    \item \textbf{Network Configuration}: Local camera connections and an LTE uplink to the cloud.
\end{enumerate}

\subsubsection{Edge Camera}
Edge cameras are deployed directly throughout the monitoring area. They are responsible for detecting the appearance of animals, capturing images, and transferring them to the edge server via local communication. Since they are intended to be deployed in large numbers in outdoor environments without commercial power, they must utilize ultra-low-power microcontrollers and be capable of operating for long periods solely on independent batteries.

The prototype uses the Seeed Studio XIAO ESP32S3 Sense. Although inexpensive, this device has Wi-Fi communication and camera functions. Furthermore, its Deep Sleep function is used with the aim of reducing standby consumption; the measured power limitations of the prototype are discussed in Section V. A PIR sensor is used as a trigger for motion detection, and HTTP communication via Wi-Fi is used to transmit images to the edge server. It uses eight AA batteries (6V) as a power source, facilitating installation in locations without power infrastructure. Fig.~\ref{fig:camera} shows an overview of the edge camera prototype.

\subsubsection{Edge Server}
The edge server connects multiple cameras to a shared LTE uplink. It performs edge filtering with YOLOv8n to select capture events with animal detections for cloud transfer. To perform these processes autonomously in outdoor environments, the small computer and communication module must be capable of continuous operation using solar panels or similar power sources.

In our implementation, a Raspberry Pi 4B is used as the small computer, and an NEC Aterm HT100LN is used as the communication module. Edge filtering uses YOLOv8n pre-trained on the COCO dataset. Its detection performance and processing time are evaluated in Section IV. HTTP communication is also used for transferring images to the cloud server. To operate this configuration continuously in an environment without commercial power, an approximately 200W solar panel and a 100Ah battery are considered as a preliminary power configuration. Final sizing requires the battery voltage, usable capacity, conversion losses, workload, and site-specific solar availability to be specified; autonomous operation with this configuration has not been validated.

\subsubsection{Cloud Server}
The cloud server verifies images forwarded by the edge server using MegaDetector v5a. This provides a second check for animal presence before notification, with the aim of reducing false alerts. Received images and detection results are stored for future analysis or model retraining.

MegaDetector is pre-trained on camera-trap images from diverse environments and is used here for animal-presence verification rather than species identification.

\subsubsection{Network Configuration}
The network has two stages. First, cameras transfer images through a local WLAN to the shared edge server, eliminating the need for individual cellular contracts. Second, the edge server forwards selected events to the cloud via HTTP over LTE. The NEC Aterm HT100LN provides both the 2.4GHz Wi-Fi access point for local connectivity and the LTE uplink. This arrangement shares one wide-area connection among cameras; coverage and concurrent operation require deployment-specific evaluation.

\subsubsection{Edge Camera Processing Flow}
The edge camera maintains a standby state using Deep Sleep mode and wakes when triggered by the PIR sensor. After waking up, it captures three consecutive images in burst mode and immediately transmits them to the edge server via HTTP communication. After transmission is complete, the edge camera returns to the standby state after a certain interval, to reduce energy consumption.

\subsubsection{Edge Server Processing Flow}
Upon receiving images from a camera, the edge server runs YOLOv8n for edge filtering. If a class corresponding to an animal is detected in at least one of the three received images, the images are moved to a storage directory and transferred to the cloud server. If no animal is detected (e.g., empty shots due to swaying vegetation), the images are not transmitted, reducing the frequency of image transmissions.

\subsubsection{Cloud Server Processing Flow}
Upon receiving images from the edge server, the cloud server performs verification using MegaDetector v5a. The server sends an email alert with the image only when an animal is detected. All received images and detection results are stored in the cloud, regardless of whether an alert is issued.

\subsection{Power Consumption Evaluation of Edge Server}
We similarly measured the power consumption of the edge server (Raspberry Pi 4B). At 5.0V, the idle current was 405$\sim$410mA (approx. 2.05W). Adding the maximum power consumption of the LTE router (approx. 6W), the resulting power estimate is approximately 8W. This combines the measured Pi idle consumption with the router maximum rating, rather than measuring the combined system under inference load.

\subsection{WLAN Communication Performance}
Under line-of-sight conditions, we evaluated communication stability while varying the distance between the edge camera and the server. Table \ref{tab:comm_perf} shows the experimental results. At close range (approx. 1m), RSSI remained stable at around -30$\sim$-35dBm. At a distance of 100m, RSSI was around -60$\sim$-65dBm, and it dropped to -77$\sim$-80dBm at the maximum distance of 200m. While connection establishment and image transfer were successfully completed without problems up to 100m, approaching the 200m point caused RSSI to fall below -75dBm, resulting in noticeable latency and communication instability. Thus, in this configuration, stable image transfer is achieved up to approximately 100m in a line-of-sight environment, while communication quality degrades near 200m, suggesting that repeaters or alternative communication methods are necessary for stable operation over longer distances.

\subsection{Reduction in Capture Events Selected for Transmission}
We evaluated YOLOv8n using images collected by commercial cameras in Kiso Town from June to November 2025. The dataset contains the intended wildlife targets listed in Section I. The evaluation unit is a capture event, normally comprising three images: there are 1,428 daytime events (4,283 available images) and 268 nighttime events (804 images). A model labels an event positive if it detects an animal in at least one available image. YOLOv8n uses a confidence threshold of 0.05 to limit missed detections, while MegaDetector v5a uses 0.25 to generate reference labels (Table \ref{tab:ai_accuracy}). These labels are model-generated rather than human-annotated ground truth. Precision is the fraction of YOLO-positive events that are also MD-positive; recall is the fraction of MD-positive events that are YOLO-positive. Thus, the reported metrics describe agreement with MegaDetector, not independently verified animal detection accuracy.

\subsection{Total System Processing Time}
We measured the overall system processing time in a stable communication environment with an RSSI of around -35dBm. The processing time on the edge side (from camera capture to completion of transmission processing at the edge server) was approximately 33 seconds (total of approx. 20 seconds for camera processing and approx. 13 seconds for edge server processing). The processing on the cloud side (from reception to completion of email notification) required approximately 11 seconds. As a result, the total time required from detecting an animal to completing an email notification to the user was approximately 44 seconds.

\section{Discussion}

In the experiment, event-based transmission reductions of 81.2\% during the daytime and 50.7\% at night were achieved. These reductions include missed detections: YOLOv8n rejected 13 of 208 MD-positive daytime events and 48 of 152 MD-positive nighttime events. Cloud verification cannot recover events discarded at the edge. Nighttime recall was 68.4\%; low contrast and the limitations of the lightweight model are possible contributing factors, but their individual effects have not been isolated. Transfer learning using nighttime camera images and comparison with alternative lightweight models should evaluate both recall and transmission reduction. Independent human annotations are needed to establish detection accuracy beyond agreement with MegaDetector.

Power consumption also limits deployment. At the measured whole-node standby power of 0.57W, 35 hours of standby alone requires approximately 20Wh delivered to the camera. This is an energy requirement, not a measured battery lifetime; capture, transmission, conversion losses, and usable battery capacity must also be considered. Improvements should verify deep-sleep entry, switch off peripherals such as the SD card and camera when inactive, and shorten active capture and communication periods. Peripheral power control is a possible contributor to standby consumption, requiring component-level measurements. SPARROW uses scheduled uplink operation and event-triggered communication \cite{SPARROW2026}; a similar duty-cycling strategy warrants evaluation here alongside its effect on notification latency.

The current results support considering deployments where cameras have clear WLAN paths of approximately 100m to an edge server with reliable power and LTE coverage, and where a notification processing time of approximately 44 seconds is acceptable. The sunny, line-of-sight communication test does not establish performance in dense vegetation, obstructed terrain, or adverse weather. Near 200m, communication became unstable. Nighttime recall and battery endurance require improvement before unattended long-term use. Long-term field operation and concurrent multi-camera performance remain to be evaluated.

\section{Conclusion}
We proposed a low-cost monitoring system for wildlife damage control. It uses a three-layer structure: edge cameras, an edge server, and a cloud server. This separates image acquisition, filtering, and notification across the three layers. The architecture connects multiple cameras to a shared LTE uplink through a local WLAN, eliminating the need for individual cellular contracts. The prototype combines edge filtering with YOLOv8n and cloud verification with MegaDetector v5a. We confirmed event-based transmission reductions of 81.2\% during the daytime and 50.7\% at night, with recall relative to MegaDetector of 93.8\% and 68.4\%, respectively. Nighttime detection and power consumption remain key limitations.

Future work will prioritize human-annotated evaluation, nighttime transfer learning, and peripheral power control. We will measure complete capture--transfer--sleep cycles and battery endurance, then evaluate obstructed links, concurrent cameras, and long-term field operation. Model and communication changes will be assessed against recall, transmission reduction, and notification latency.
