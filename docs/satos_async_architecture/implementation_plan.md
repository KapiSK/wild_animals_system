# Gmail画像保存システムの安定化計画 (satos_async_architecture)

既製品カメラから送信される動画ファイルが `.mov` 形式であることが確認できました。フォーマットの不一致による読み飛ばしではないため、不安定動作の根本的な原因は**「直列処理によるネットワークと処理のブロッキング」**に絞られます。

本計画では、ポーリングやネットワーク転送、および**YOLOを用いた重い画像の推論処理**による遅延が蓄積しないよう、システムを再設計します。

## 課題の明確化と背景

現在の `gmail_image_saver.py` は、以下の処理をすべて**1つのメインスレッドで直列に**実行しています。

1. Gmailからのメールポーリングと動作検知時の動画ダウンロード
2. `ffmpeg` を用いたフレーム画像切り出し（3枚）
3. **YOLOによる動物・人物の推論検知**（`ENABLE_LOCAL_YOLO=true` の場合）
4. クラウドサーバーへの画像アップロード（HTTPS POST要求×3）

YOLOの推論は特にCPUに重い処理です。これを並列化せずに実行すると、クラウドサーバーの応答待ちやffmpegの処理中、推論中にシステムは「次のメールの受信確認」を完全に停止してしまいます。これが累積することでシステムがスタックし、動作が不安定になります。

## 提案する変更内容 (Proposed Changes)

以下のアーキテクチャ更新を行い、全体の安定化を図ります。

### 1. アーキテクチャの完全非同期化（Producer-Consumer パターン導入）
Pythonの組み込みライブラリである `queue.Queue` と `threading` を利用し、タスクを分離します。

* **Producer スレッド（メインプロセス）**
  定期的にGmailにアクセスし、該当メールがあれば動画ファイルとしてダウンロードします。ダウンロード完了後、「対象の動画ファイルのパス」だけをキュー（Queue）に登録し、すぐに次のメール確認や待機(POLL)に戻ります。これにより、どれだけ重い処理があったとしても「メールからの動画取得」が遅れることは無くなります。
* **Consumer スレッド（ワーカースレッド）**
  バックグラウンドでキューを監視し、新しい動画パスが渡されたら以下の処理を直列で実行します。
  A. `ffmpeg` でのフレーム抽出
  B. （ONであれば）YOLOのモデルを用いた推論処理
  C. 対象物があった場合のクラウドサーバーへのアップロード処理
  ※ エッジサーバーのリソース（メモリ）枯渇を防ぐため、Consumerスレッドは1つ（または設定された数）とし、順次安全に処理を消化する構成とします。

### 2. 再試行とバックオフ処理の強化
一時的なネットワーク切断や、Gmail側の一時的な接続制限（Rate Limit）に対し、現在の30秒待ちではなく、「指数関数的バックオフ（徐々に待機時間を延ばして再試行する）」を導入し、プロセスが完全に停止することを防ぎます。
