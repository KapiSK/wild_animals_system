# 統合サーバーの同時処理時のイベント分離仕様の修正

## 背景と問題の所在
現在、複数のメール（既読を未読に戻したテストケースなど）を同時に処理した際、同じカメラで撮影されたものがクラウドサーバー側で「同じサイクルID」にまとめられてしまう問題が発生しています。

これは以下のクラウド側の仕様が原因です。
1. クラウドサーバー（`server.py`）は、統合サーバーから送られてきた「カメラID」と「シーケンス番号」の組み合わせを見てイベントをグループ化します。
2. 統合サーバーは、メールの添付ファイル名（例: `KD1_000121.mov`）からシーケンス番号（`000121`）を抽出しています。
3. そのため、同じ添付ファイル名を持つ複数のメールが同時に処理されると、すべて同じ「カメラID(`KD1`)・シーケンス番号(`000121`)」としてクラウドに送られます。
4. クラウド側は「同じシーケンス番号がタイムアウト時間内（300秒以内）に届いた」と判断し、これらをすべて同じイベント（同じサイクルID）に結合してしまいます。

## 解決策の仕様（統合サーバー側の改修）

この問題を解決するため、統合サーバー (`satos/gmail_image_saver.py`) に対して以下の仕様変更を行います。

### 1. カメラIDの確実な抽出
`_maybe_save_mov_part` 内で、ローカル保存用のカスタマイズされたファイル名からではなく、**メールに添付されていた元のファイル名** から直接「カメラID」を抽出します。これにより、ファイル名設定によるカメラIDの汚染を防ぎます。

### 2. シーケンス番号をUIDベースに変更（最重要）
クラウドサーバーに送信する「シーケンス番号」として、元のファイル名の連番（`000121`など）を使用するのをやめ、代わりに **「メールのUID」と「パート番号」を結合した数字（例: UIDが123, パートが1なら `1231`）」** を使用します。
- UIDは各メールに対して一意であるため、同じファイル名の動画が複数あっても、それぞれ全く異なるシーケンス番号が割り当てられます。

## クラウドサーバー側の仕様変更の要否

**今回の方式であれば、クラウドサーバー側の改修は「不要」です。**

クラウドサーバー側の `/upload` エンドポイントは、シーケンス番号として「数字（`\d+`）」が送られてくることを期待する正規表現になっています。UIDも数字であるため、この仕様に完全に合致します。
統合サーバーがメールごとに一意なシーケンス番号（UID）を送るようになるため、クラウドサーバーは既存のロジックのままで自然にそれらを別々のイベント（異なるサイクルID）として処理するようになります。
